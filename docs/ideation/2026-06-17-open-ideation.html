Grounding Context

Codebase Context. AI Briefing is a TypeScript/Node (ESM) pipeline with a thin orchestrator (src/index.ts) and seven stage modules. State lives in git plus docs/episodes/*.json sidecars — no database. The daily flow: fetch (12 RSS sources, 2 already dead) → curate (Claude Sonnet clusters duplicates and scores importance 0–100, keeps 1–6 stories over a 45 threshold, with a stable kebab-case canonicalKey per cluster) → script (single narrator, 3 personas rotating daily, depth scaled to importance) → tts (OpenAI gpt-4o-mini-tts or OpenRouter Gemini; per-section single request, oversized parts fall back to chunked synthesis) → audio (ffmpeg, EBU R128 −16 LUFS, chapters) → publish (MP3 + sidecar + transcript, regenerates feed.xml). It runs unattended on a weekday GitHub Actions cron.

Strategy. The product commits to a hard ~10-minute ceiling and a fully automated daily pipeline (no human in the loop), serving one veteran senior engineer who wants AI signal in minimal time. Tracks: curation quality, audio/voice quality, pipeline reliability. The three strategy metrics are story relevance (qualitative, no measurement loop today), episode length, and cost per episode.

What ideation leaned on. Two structural facts shaped the strongest ideas: (1) ~15+ episodes of structured sidecars and transcripts accumulate but no future episode ever reads them — curate runs cold every day; and (2) external research that news importance is fundamentally a cluster property (size + source entropy), and that single-source over-confidence (the WaPo AI-podcast failure) and silent degradation are the canonical failure modes for automated news audio.

M1

Cross-episode memory ledger & story threading

Curation · Top pick

Description. Persist each episode's canonicalKey clusters into a rolling ~14-day ledger that curate reads on the next run. The briefing gains continuity: suppress stories already covered unless they genuinely developed, and have the narrator deliver follow-ups — "yesterday we flagged this as a rumor; today it shipped." The prior episode's caveat becomes today's setup. A ~50-line JSON written by publish, read by curate; no database.

Basis
direct: canonicalKey already exists in curate.ts; publish.ts already reads the episodes dir; the verifier confirmed curate never reads prior episodes. external: importance evolves across days as cluster source-entropy grows (arXiv 2402.10302).
Rationale
A daily listener's marginal value is the delta, not a re-briefing. Memory is the difference between a feed and a correspondent who remembers what it already told you — and four other ideas (threading, week-in-review, velocity ranking, the feedback loop) are downstream of it.
Downsides
Introduces cross-run state that must stay consistent; ledger schema and retention need care; exact-key matching misses reworded recurrences (an embedding index would close that, at added cost).
Confidence 90%Complexity MediumSpine: M1→M18→M21→M15
M14

Personalized salience — curate for this engineer, not a stranger

Curation

Description. The pipeline scores relevance as if an average reader is listening, but there is exactly one listener with a known stack and concerns. Add a lightweight interest profile (languages, tools, "I ship in TypeScript/Node," topics that matter to my work) that re-weights cluster importance scores in the curate prompt. Same pipeline, personalized salience.

Basis
direct: the primary user is precisely specified and the product is explicitly personal; the relevance metric is qualitative with no input today. external: personal-briefing products (WaPo, Alexa) assume per-user relevance as the core value.
Rationale
For an n=1 product, generic scoring leaves the single biggest lever — fit to this person — completely unpulled. The verifier flagged this as unusually tractable precisely because there's no multi-user infrastructure to build: it's a profile file injected into a prompt.
Downsides
Risks a filter bubble that misses important-but-off-profile stories; needs a floor so genuinely major news surfaces regardless of profile fit.
Confidence 85%Complexity MediumPairs with M15 (ratings)
M3

Curation observability — stop deleting the editorial verdict

Curation · Reliability

Description. curate ranks all clusters, thresholds at 45, slices to the top stories — then discards everything below the line with no record. Persist the full scored cluster list (including dropped clusters with their importance + category) into the episode sidecar, and accumulate a per-run health report that flags every degraded path (the chunked-TTS fallback, a provider fallback, a stale source). This costs zero extra LLM calls — the data already exists in the parsed response; it's dropped on the floor.

Basis
direct: the verifier confirmed curate.ts logs only the selected clusters and the sidecar carries no curation metadata; the dropped clusters and their scores are thrown away after selection.
Rationale
This is the measurement substrate every later curation experiment depends on — you cannot tune a threshold you cannot see — and it doubles as the observability the unattended pipeline lacks. Cheapest high-leverage item in the set.
Downsides
Larger sidecars; to surface dropped clusters as audible content (the "didn't make the cut" close) they'd need threading through to script, which is more work than the logging itself.
Confidence 90%Complexity SmallUnlocks M14, M15 tuning
M9

Pronunciation lexicon for AI & lab names

Audio/Voice

Description. AI news is unusually dense with names TTS will mangle — Qwen, Mistral, Hugging Face, researcher names, lab acronyms. Maintain a small versioned project lexicon; a pre-TTS pass rewrites known terms to phonetic spellings (or SSML phonemes where the engine supports them), and unknown new-entity names get flagged in the run report for one-time addition. Optionally add an STT round-trip "canary" on the first 30 seconds to catch divergence before rendering the full episode.

Basis
external: the WaPo AI podcast's documented failure was hallucinated name pronunciations; gpt-4o-mini-tts takes natural-language instructions, Gemini 2.5 Flash TTS supports SSML. reasoned: AI vocabulary is adversarial for TTS and recurs daily, so a curated lexicon has outsized, compounding payoff. Verifier: no pronunciation handling exists today, and the instructions field is already wired in tts.ts.
Rationale
Clean episodes depend on names being right; this targets a known, named failure mode for exactly this content domain, and the fix slots into machinery that already exists.
Downsides
Lexicon needs ongoing curation as new models/labs appear; phonetic spellings are engine-specific and may need redoing on a TTS swap.
Confidence 85%Complexity Small
M16

Confidence calibration — source count drives epistemic stance

Audio/Voice · Curation

Description. A fully-automated pipeline has no editor to say "we only have this from one place." Borrow the newsroom two-source rule: facts from a single-source cluster get hedged language ("one report claims…") while multi-source clusters are asserted plainly, and likely-overhyped stories get a skeptical beat. Source entropy — which the curator already computes — is the corroboration count.

Basis
direct: the sources array exists per cluster and is already passed to the script stage; there is one narrator with a caveat field not currently conditioned on source count. external: journalism's two-source corroboration norm; the WaPo over-confidence risk.
Rationale
The cardinal risk in automated AI-news is credulous hype relay to a sophisticated listener who can smell over-confident single-source claims. Encoding corroboration into the narration's epistemic stance is the cheapest defense, and it's a prompt change — no new infrastructure.
Downsides
Over-hedging can make the show sound wishy-washy; the "overhyped" judgment is itself a model call that can be wrong.
Confidence 80%Complexity Small
M7

Dead-man's-switch for the unattended run

Reliability

Description. There's a weekday cron but nothing notices when it silently fails to produce an episode. Add Healthchecks.io start/done pings with a 25-hour window (absorbing GitHub's scheduling jitter): ping on start and on successful publish; a missed ping pages you. The canonical solo-operator pattern — one env var and two lines.

Basis
external: dead-man's-switch monitoring (Healthchecks.io, 25h window, start/done pings) is the standard unattended-pipeline pattern. direct: the verifier confirmed no watchdog exists anywhere — the cron either succeeds or sets a non-zero exit code with no external alert.
Rationale
Pipeline reliability is a named track, and the worst unattended failure is the one you discover days later because episodes simply stopped. This is the floor of unattended operability — cheap, standard, and currently absent.
Downsides
An external dependency (the monitoring service); distinguishing "no news today" from "pipeline died" needs a start ping, not just a done ping.
Confidence 90%Complexity Small
M6

Content-hash stage caching

Reliability · Cost

Description. index.ts runs fetch → curate → script → tts → audio → publish as one linear try block; any failure (a publish-time rebase race, a TTS timeout) re-runs everything on retry, re-billing the expensive curate and TTS stages. Hash each stage's input, write stage outputs keyed by hash, and skip stages whose input is unchanged. A failed publish should never re-synthesize audio.

Basis
external: idempotency via content-hash stage caching is a standard ETL pattern ("re-run skips completed stages"). direct: the verifier confirmed index.ts is a linear try with no skip logic and there is no publish retry on rebase failure.
Rationale
Cost per episode is a named metric, and the most wasteful spend is re-running paid stages to recover from a cheap downstream failure. Caching makes reruns nearly free — which in turn makes aggressive retries (and a publish retry loop) affordable.
Downsides
Cache invalidation is its own complexity; needs a clear hashing boundary per stage and a place to store intermediates (tmp or committed scratch).
Confidence 80%Complexity Medium

Cross-cutting synthesis

The surprise-me frames converged on one compounding spine worth seeing as a program rather than four separate tickets: M1 (memory) → M3 (observability) → M14 (salience) → ratings together build a self-tuning personal editor. The ledger gives the show history; observability makes its editorial judgment legible; salience personalizes the scoring; and a one-tap rating loop (cut this round as dependent on M1, but a strong follow-on) closes the relevance metric that has no measurement today. Each is shippable alone, but built in sequence they raise the same curve — story relevance — from three different angles. Two cut-but-notable extensions ride on M1: a Friday "what changed this week" meta-episode synthesized from the week's sidecars (zero new fetch), and velocity ranking that rewards a story accelerating across days, not just one that's big today.
